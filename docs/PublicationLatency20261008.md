# 三连拍结果可读时延修复（2026-10-08）

## 问题与结论

用户报告的 2026-09-17 十组三连拍：Evidence 首次可读为 10.22–27.46 秒，平均 18.19 秒；九组有 Result，一组无可见绑定面板而跳过。该报告附件本轮未能独立读取，不能仅由这些总时延断定 OCR 或 NAS 是瓶颈。本轮基线为 `main` / `fbe9d4dffa64e06ebb737216b6ba4d8fb222fc0c`，开发分支为 `codex/ocr-result-latency`，使用隔离工作树与临时数据。

代码确认的固定等待与诊断缺口：归档每批最多 20 个版本，每轮无论是否还有待处理版本都等待 3 秒；OCR 的旧总时长混合调度、定位、模型准备与预测；归档仅保存最近一次发布实测耗时。已有快速事件发布先于历史导航重建，但可读时间确认要等历史重建才能回显到 Evidence，导航失败时文件和查询的时间元数据可能不一致。

## 变更

- 归档有到期任务时立即续批，无到期任务时每 0.5 秒检查；尚有到期回执时不开始历史导航重建。发布异常仍等待 3 秒，每个失败版本继续遵守原有持久化重试退避。此为调度上限改善，不是端到端 SLA；文件系统操作阻塞仍可能延长等待。
- 每个不可变回执版本保存 `publication_started_at`、`receipt_publication_ms`；`archive_queue_wait_ms` 从该版本排队到本次成功发布尝试开始，以墙钟计算，包含重试/退避等待。`receipt_publication_ms` 用同进程单调时钟测量原件校验、留存和不可变回执发布。查询、Evidence 的 `observations[].archive`、全量索引均可逐版本读回。旧 `archive_queue_ms` 仍是排队至回执发布完成的兼容字段。
- 快速事件文件发布后，在历史导航开始前用第二次局部发布回显 `readable_at`。确认与待回显版本集合在同一数据库事务保存，NAS 回显失败仍可局部重试。该时间保留首次成功发布的写入端依据，不代表另一台客户端首次读取。导航失败仍保留 pending 状态与恢复路径，原始回执和照片不回写。
- OCR 计时拆出调度等待、整次识别执行、模型锁等待、模型准备和预测调用，旧字段保持兼容。模型调用时长包含适配器内的远端队列、传输与服务处理，不能称作 GPU 纯推理时间；细阶段存在嵌套，不能直接与总时长重复相加。
- 验收脚本使用可被真实 ArchiveStore 接受的 `FieldRecognitionArchive` 目录，逐组检查三张源照片、全部任务终态及全部 Result 的 SHA-256。报告保留每任务阶段值及其时钟依据、缺测数量，区分首个 Evidence、整组终态 Evidence、首个 Result、全部 Result 可读。跳过而无 Result 为可解释终态，不当作丢失或成功读数。

归档表扩展由 ArchiveStore 启动时幂等增加两个可空列，不重写业务记录，不回填旧阶段值。该运行代码仍需按升级入口检查，不允许在线直接替换共用源目录。

多个托管角色启动时，归档列检查/扩展用 SQLite IMMEDIATE 事务串行执行，防止并发重复加列；旧版本文档保持不变。

OCR 新字段为 `ocr_scheduler_wait_ms`、`ocr_execution_ms`、`ocr_model_lock_wait_ms`、`ocr_model_prepare_ms`、`ocr_model_call_ms`，同时保存调用次数、适配器范围和阶段包含关系。依赖失败后再领取的 `queue_wait_ms` 沿用原提交时间至最新开始时间，可能包含早前失败与退避；新执行细阶段对应完成回执中的那次执行，不能还原所有历史尝试。代码存在远端轮询超过 12 秒后延迟 15 秒再认领的路径，需任务故障记录佐证，不能按历史最长 27.46 秒反推已经发生此路径。

## 验收与阈值

复测命令及独立实例配置见 [结果发布复测说明](PublicationRepairNotes.md#隔离现场复测)。默认十组、每分钟一组三张，`record_scope=test_only`。t0 为末张文件写入、fsync 和 rename 完成后客户端记录的时间。端到端延迟由写入与读取的同一客户端进程单调时钟测量；NAS mtime 和跨进程阶段差值单独标注，不能混作同一时钟。

阈值由产品/验收确认后才传 `--evidence-target-ms`、`--result-target-ms`；未配置时不报告合格/不合格。超时仍保留已见任务、跳过原因及阶段值。十组统计只描述该次批次，不证明长期稳定性。新旧版本对照须使用同样照片、相同输入节奏及可比负载，同时保存源照片、任务、清单和哈希。

一致快照耗时是本轮读到终态 Evidence 并核对其全部 Result 完成的客户端时间，不能取历史各文件首次出现时间的最大值冒充当前一致快照。首次终态后，脚本继续观察同组、同任务集合、同 Result 清单/发布 generation 的归档时间回显，最多额外等待 `--metadata-timeout`（默认 5 秒）；它不改写首次可读耗时。确认未出现时单独标记元数据缺测/超时，不把业务结果改为超时。

- `PROVEN`：上述自动测试实际覆盖的调度和计时契约、结果清单一致性及失败恢复。
- `PARTIAL_EVIDENCE`：用户提供的历史十组端到端观测；本轮未独立读回附件。
- `NOT_PROVEN`：新版本现场 NAS 三十任务延迟分布、最终阈值达标、长期稳定性及实际仪器准确率。

API、相机、OCR、归档服务保持当前运行版本；本轮不调用服务启停、不修改部署目录。先提交测试版本，再从部署目录运行 `scripts/upgrade_runtime.py --revision <SHA>` 只读检查；运行代码按现有约束保留待部署。进程身份和健康检查仅证明本轮未触发服务重启，不能替代新版本现场识别验收。

## 退回记录复测后的追加修订

2026-09-21 的退回记录补充了 Result 首次可读 171.55 / 205.20 秒。本地找到六张原照片，原件哈希与历史 Evidence 相符；照片本身未解出二维码。隔离实例通过实际解码项目标签建立新的 test_only 绑定，没有恢复线上已过期绑定。

首版候选 `ed59522` 在独立 NAS 目录完成十组、三十任务回放，任务均有终态，完整终态清单核验耗时 24.97–69.09 秒。这个结果仍有波动，不能宣称稳定解决；本轮显式 PhotoReceipt 把同组三张聚合成一个 Result，与退回批次无回执、逐图独立结果的协议不同。首个 Result 字节提前可读不等于三任务完成，数值为空或候选冲突也不能当作识别正确。实际记录保存在忽略目录 `Verification/PublicationLatencyAcceptance20261008/`。

追加修订在第二隔离分支 `codex/ocr-result-latency-final` 开发：

- 快速发布先定位待发布/待回显版本，只读取其事件关系闭包及全部版本。反向关系使用实体标识、已有事件路径账本和业务表的标识查询；输出文档仍来自已归档快照。不会先加载全仓历史 document 再筛选事件。完整导航仍是全历史维护，元数据及路径账本的规模开销仍存在。
- 完整性巡检用独立运行锁避免重复巡检，路径迁移锁仅用于定位并打开文件。持有文件句柄校验字节时，归档发布与迁移可继续。CIFS 迁移可能刷新缓存时间属性，检测到校验期间属性变化时最多重新打开一次；随后仍校验不可变回执/原件的预期 SHA-256，不豁免篡改或文件缺失。
- 历史 JSON 准备、索引逐行构建和导航 JSON 编码增加合作检查点，让新到期回执能够中止维护并优先处理。单次文件系统操作和序列化片段仍可能阻塞，检查间隔不是端到端硬阈值。
- 补记 `vision_queue_wait_ms`，表示本任务取得云模型调用槽位的等待；多面板任务按自身面板累加，与 `vision_ms` 的实际调用耗时分开。两者仍不能与包含它们的总处理时长重复相加。
- NAS 观察器跳过 `.System` 回执目录，按活动事件观察时剪枝已完成事件；活动 Evidence/Result 每次仍读取真实字节并验证哈希，不用 mtime 或缓存内容证明当前快照。原协议复测的注入与读取分线程，以单调时钟的绝对分钟计划记录实际注入间隔和读取轮次耗时。

首版实测与追加修订的结果不得合并统计。追加版本仍须完成原无回执流程复测，且现场 Windows `Z:` 首读、生产历史负载、产品阈值和不停机替换部署均是独立验收门槛。代码回归、六张历史照片回放和服务健康响应不证明长期稳定性或仪器读数准确率。

追加修订完整回归为 **648 passed**，两条既有依赖弃用提示；Python 编译和 diff 检查通过。以生产数据库只读备份的 6474 个已归档版本、113,875,999 字节 document 验证两个事件闭包，其来源/任务/版本与全量准备一致，局部准备约 2 毫秒；这是本地准备校验，不是 NAS 发布 SLA。CIFS 测试目录内的迁移中原图校验经过一次属性刷新重开，最终哈希与原照片一致。独立审查还补上早期 standalone Evidence 只有内部 capture 标识时的观察恢复测试，防止读者剪枝产生假超时。

## 原协议实测与归档优先级修订

候选 `a4d84df` 已按原无 PhotoReceipt 协议完成另一轮十组、每分钟三张。三十任务全部终态，生成三十个独立物理 Result，十组终态快照均通过清单哈希验证。每组全部 Evidence 首次可读为 3.33–70.01 秒，全部 Result 为 19.43–117.95 秒，完整终态快照为 23.64–122.99 秒；三任务归档时间回显超时，其余二十七任务完整。原始测量不因后来回显而回填。故该版本仍为 `NOT_PROVEN`，不能宣称时延问题已解决。

归档数据库证实预热时十八条 FIFO 回执发布共耗 51.12 秒，三个终态版本排队 61.43–68.10 秒；最后终态回执发布后，事件可读确认还等待 45.48 秒。该范围包括巡检报告发布及事件生成，旧阶段计时不足以进一步归因。局部事件闭包消除了无关 JSON 解码，却没有消除批内进度回执阻塞和重复 NAS 路径访问。

随后修订每处理一条就重新选择：最新终态及其最新来源、明确组、成员、重试及确认依赖优先，固定历史 FIFO 配额保留进展；失败依赖继续遵守退避。必要依赖全部归档后才发布该事件，旧版本始终保留并最终补发。Evidence 的 `archive.history` 说明事件历史回执总数、已发布数及待补数量；`complete` 仅表示这些回执已发布，不表示全量巡检通过。晚补历史不会降级最新任务。

固定配额为三次优先选择后一次最旧到期历史版本，跨批次保留计数；这是选择次数公平，不是等待秒数保证。单次 NAS 操作不可被中途抢占。独立事件的视图发布及时间回显失败分别保存持久退避，坏事件保持未确认，不能在队列入口阻止其他事件的原始回执或业务文件发布。事件计时记录失败独立显示，不能覆盖真正的发布异常。

同一回执发布共用一个路径账本；单次事件发布与时间确认共用本次已经校验并放置的照片，不跨发布缓存原件真实性。路径检查仍真实解析子路径；同位置照片也读取字节验证 SHA-256 和大小。不可变回执的全部所选历史依旧逐次读取并校验 SHA，不用文件大小或时间属性代替证据校验。

事件发布逐次保存本地 SQLite `archive_meta` 的 `event_publication:<摘要>` 阶段实测，区分路径账本加载、事件闭包/准备、回执校验、照片放置与视图生成、业务文件写入、确认准备与回显写入；均注明进程单调时钟。照片放置与视图生成仍为一个合计阶段，不能把它直接称为 NAS 纯写入耗时。失败阶段也保留，重试相同版本集合记录最近一次尝试；不是全部尝试的独立审计。

第三轮候选的实测、完整回归及升级检查尚待记录。线上运行代码未被替换，Windows Z: 首读、真实现场负载、产品阈值和不中断部署继续是独立门槛。

终态优先与事件故障隔离候选的完整回归为 **674 passed**（110.99 秒），两条既有依赖弃用提示；改变的 Python 编译与 diff 检查通过。新增实际临时文件验证：旧回执损坏时，独立新事件仍归档并生成可解析终态 Evidence；坏回执保持原字节和未确认，退避后恢复可补发。此前 672 项测试日志保留，新增故障边界通过后才继续真实 NAS 实测。
