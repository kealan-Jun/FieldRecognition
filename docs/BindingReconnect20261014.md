# 短暂断流后的绑定延续（2026-10-14，已部署）

## 现场问题与证据

相机 `lubancat-0282f88a_cam02` 的本机记录显示：19:41:20–21 完成两台仪器绑定；19:44:55 的照片保留有效归属；19:46:54 出现 `camera_stream_error`，两条绑定结束；19:46:56 Receiver ingress 从 10 变成 5。之后的照片拍摄时没有有效绑定，直到 20:06:55–20:07:02 重新扫码。

用户提供的板端日志截图显示同一时段 `Connection refused`、发送进程启动时间未变化及持续的采集 FPS。它支持接收端暂时不可用后重连的排查方向，但本项目没有独立读取 Receiver 或板端日志，不能由 FPS 推导媒体持续送达，不能声称已证明接收端重启或物理设备关机。

另一张截图说明换卡曾使身份从 `lubancat-14d632c0` 变为 `lubancat-0282f88a`。这是独立的身份变更；上述 19:41 绑定和后续照片本身都已使用新身份，不能把 19:57–20:05 的空档归因于此次换卡。恢复机制只对精确相同的相机身份生效，不自动建立别名、不跨设备迁移绑定。

## 运行规则

Receiver 适配器明确标记的短暂传输故障，包括读取/解码报错、持续无新帧、状态接口暂不可用、相机暂时缺失、媒体在线信号丢失及 ingress 变化，在已有在线状态和有效关系的前提下，进入固定 **30 秒**的恢复窗口。窗口从第一次异常开始，后续报错不会延期。

- 仪器和场景关系保留原 ID、人员、扫码凭证和独占占用；页面显示“短暂断流，绑定暂存”和恢复截止时间。
- 必须同时恢复在线状态和一秒内的新解码画面，才延续原关系。只有心跳无法恢复。ingress 变化会清除缓存，旧会话画面不能证明新会话已恢复。
- 暂停和恢复两端均作废之前的扫码凭证；延续已有绑定不等于允许旧扫码凭证创建新绑定。
- 窗口到期即自动结束关系，原因 `camera_reconnect_timeout`；后台维护可在没有新状态回调时执行。恢复后仍须新扫码，不复活已结束关系。
- 明确 `device_boot_id` 改变、采集进程退出/无响应/重新配置等确定的本地会话结束仍立即释放。手动结束不会被恢复覆盖。北京时间零点仍按零点结束。
- 缺少设备来源的启动 ID 时，同一相机在窗口内重连按有界的连续使用策略延续；这不是设备没有重启或使用人没有变化的物理证明。需要更强保证时，上游应提供可靠的设备启动 ID。

没有先前在线状态、没有有效关系，或未标记为可恢复的服务故障，继续按明确释放处理。内部观察接口不把所有 `online=false` 一概当成可恢复异常，监督进程的退出信号不会被宽限。

## 时间归属与归档

绑定文档追加 `service_interruptions[]`，保留首次异常时间、固定截止时间、原因、旧 ingress、恢复时间及新 ingress。`connection_status` 为 `recovering/connected/ended`；恢复时清除 `reconnect_deadline`。生命周期版本为 `camera-service-session/2`，每日二维码授权仍为 `daily-qr-binding/1`。

每次变化通过原有数据库事务和归档 outbox 留证。原扫码和既有照片回执不改写；不需要数据库模式迁移。已结束历史绑定不会回填为有效。

恢复窗口只保留占用，**不授予断流空档的照片仪器归属**。时间包含规则排除 `[异常开始, 恢复时间)`；晚到照片同样执行该规则，空档任务标记 `attribution_status=needs_review`、`attribution_reason=camera_connection_interrupted`。恢复前后的照片继续按各自拍摄时间取关系。已经保存的照片与任务快照保持原证据语义。
