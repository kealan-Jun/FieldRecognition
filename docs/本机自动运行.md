# 本机自动运行

适用于 `/home/x1/Projects/FieldRecognition` 所在的这台 Linux 电脑。接收端、相机和语音照片目录沿用本机配置；识别服务使用独立 Python 环境，本机已配置 GPU OCR（见 [GPU 部署](GPU部署.md)）。程序不改动现有 Agent、Receiver 或 VisionCortex 服务。

当前采用本机后台识别、读取 NAS 语音照片、向 NAS 独立目录留存的部署方式；无需在 NAS 部署服务或取得管理员账号。归档路径、内容、断线补传及状态检查见 [本机运行与 NAS 留存](本机运行与NAS留存.md)。

## 第一次使用

打开 [现场识别页面](http://127.0.0.1:8188)，在页面上方填写**实验员姓名或编号**，点击“保存并开启自动运行”。该登记由使用者明确填写，按相机保存在本机数据库，不从系统用户名、浏览器旧记录或历史测试绑定推断。

随后让仪器码进入挂脖相机画面。系统自动扫描，唯一且已登记的仪器码在一帧成功解码即可绑定，不要求先扫场景码；已有实际扫码场景时仍校验场景冲突。启用照片监控时后台预加载并常驻 PaddleOCR，等待用户对现有 Agent 说“拍照”；新照片保存到 NAS 并稳定后执行识别，沿用单张任务 5 秒无数字时的阿里云兜底规则。网页自动显示结果，Agent 对话播报仍需接入已有查询工具。

打开网页用于登记、查看或人工处理；关闭网页不会停止后台自动扫码或照片监控。配置了挂脖主码流时，打开页面自动显示实时画面；视频连接中断后自动重连。可点击“关闭实时视频”隐藏画面，后台扫码仍继续。未登记时，服务显示“等待实验员登记”，不会创建自动绑定。

## 换人、暂停和结束

| 操作 | 结果 |
|---|---|
| 暂停自动扫码 | 停止自动创建新绑定；已有绑定、OCR 模型和语音照片监控保留。暂停状态跨本地服务重启保存。 |
| 主动结束本次绑定 | 结束当前使用关系，同时暂停该相机的自动扫码，避免刚结束就重新绑定。 |
| 更换实验员 | 先结束当前绑定，再填写新人姓名或编号，点击“保存并开启自动运行”。历史记录保留原实验员。 |
| 设备采集会话改变 | 结束旧绑定与场景关系，自动等待重新扫码；短暂离线但会话未变时保留当天绑定。 |
| 北京时间跨日 | 当天零点结束旧仪器和场景关系，即使设备仍开机也必须重新扫码；晚到照片保留拍摄时的历史归属。 |
| Receiver 状态暂不可用 | 暂停自动扫码，等待可确认的在线状态；不单凭 HTTP 失败结束已有绑定。 |
| 多码、未知码或场景冲突 | 自动扫码暂停并持久化该暂停状态，页面提供命中照片；人工核对或选择后再明确恢复。 |
| 本机识别程序重启 | 恢复登记、启用／暂停设置和照片去重记录；取得新的设备状态后沿用仍有效的绑定。 |

**设备状态边界：** 当前仍使用 Receiver 的 `rgb_ingress_session_id`；设备重连或 Receiver 重启也可能改变它，尚不能严格等同于设备进程启动 UUID。自动运行改造没有改变这一上游边界。

## 本机启动入口

应用菜单中的“现场识别”入口会启动本项目用户服务并打开网页。终端也可以在项目根目录执行：

```bash
.venv/bin/python scripts/control.py open
.venv/bin/python scripts/control.py status
.venv/bin/python scripts/control.py start
.venv/bin/python scripts/control.py stop
```

本机以 `field-recognition.target` 管理 API、相机监控、OCR、归档四个服务，见 [托管运行](ProductionRuntime.md)。自启由该用户服务的 enable 状态与本机用户的 linger 设置配合；异常退出沿用 systemd 的重启机制。正常停止不会删除登记或数据。诊断命令：

```bash
systemctl --user status field-recognition.target
systemctl --user is-enabled field-recognition.target
loginctl show-user x1 -p Linger
journalctl --user -u field-recognition-ocr.service -n 50 --no-pager
```

配置与凭证继续由未跟踪的 `.env` 加载。`FIELD_AUTO_RUN_ENABLED=1` 只决定**尚未保存设置**时的默认启用状态，仍需本人登记实验员；保存后以数据库中的设置为准，环境默认值不会覆盖人工暂停。

## 自动运行接口与实现

- `GET /api/automation`：相机、登记、自动运行状态及自动扫码会话。
- `PUT /api/automation`：提交 `{"enabled":true,"operator":"使用者填写的姓名或编号"}` 保存登记并开启，提交 `{"enabled":false}` 暂停。
- `GET /api/state`：新增 `automation`，现有 `photo_watch`、`ocr`、`bindings` 和 `jobs` 保持可用。
- 旧连续扫码接口创建 `owner=browser` 的会话，仍有 20 秒续期要求。后台创建 `owner=automation` 的会话，没有网页租约；网页关闭只取消自己创建的手动扫码会话。

[automation.py](../automation.py) 每秒检查当前目标，使用 [live_scan.py](../live_scan.py) 的同一把锁串行处理启停、登记变更和扫码写入。启动自动会话时记录已解码帧编号，等待之后的新帧；解码完成后再次检查设备状态。绑定成功后继续查找尚未关联的二维码，当天同一仪器或场景不重复绑定，扫码异常至少等待 30 秒再重试。新登记、绑定和主动结束共用锁，防止换人或取消之后旧扫码写入新关系。

SQLite 的 `automation_settings` 以 camera 为主键，保存 `enabled`、`operator`、`registered_at`、`pause_reason`。既有二维码 ID、原图、绑定记录和任务记录不重写。文件监控与读数执行仍由 [photo_watch.py](../photo_watch.py)、[panel_readout.py](../panel_readout.py) 负责。

## 验证边界

自动测试通过临时数据库、模拟相机、真实二维码样张解码及模型替身验证：首次等待登记、关闭页面不影响扫码、单帧绑定、会话重启后重新扫码、暂停持久化、多码暂停、取消竞态和换人隔离。它们证明代码规则，不能证明实际标签成像质量或真实仪器读数准确率。

本机实际重启整台电脑、设备采集服务实际停启和真实仪器语音读数闭环，均需要单独的现场验收。相关历史证据与完整机制见 [技术方案](../技术方案.md) 和 [运行与验证记录](运行与验证记录.md)。

## 工作台与操作记录

工作台、仪器登记、操作记录使用独立导航，切换页面不暂停后台扫码。工作台集中显示实时画面、当前绑定与面板读数；实验员登记及单张拍摄等工具可展开，二维码命中帧以原图缩略凭证展示。样式和脚本使用内容哈希版本，首页要求重新验证缓存，防止更新后混用旧资源。

`GET /api/state.activity` 从现有扫描、场景关系、绑定和读数回执生成最近 50 条时间记录，配置相机时只展示该相机。扫码识别不依赖绑定成功才可查看；开始与结束使用分别显示，读数中断采用数据库中的实际任务状态。新视频扫码记录登记的实验员及扫描会话编号；旧记录没有的人员信息显示“当时未记录”，不按当前实验员补写。该列表是持久化回执的只读展示，不会为普通视频帧新增保存操作，也不改写历史时间和原图。

桌面宽度至少 1000 px 时，“扫码与读数”采用窗口等高布局：视频按剩余空间等比例显示，绑定与读数卡片同屏，默认状态无需滚动整页。登记设置和额外工具展开为浮层；长读数结果可在卡片内查看，窄屏保留正常滚动以保证可读性。已在用户当前 1480 × 694 窗口核对，三张主要卡片及操作按钮全部位于可视区域，卡片默认内容没有溢出。

语音照片不再依赖仪器绑定：未绑定也读取、识别和留存，仪器/场景保持空值。轮询和稳定等待均为 0.5 秒；逐阶段耗时、补处理窗口和照片归属规则见 [识别时延与未绑定照片](识别时延与未绑定照片.md)。视频按原比例适配深色容器，绑定凭证默认折叠，最新语音照片和读数位于右侧主要区域。

操作记录增加照片缩略图、可展开的阶段耗时、任务回执和关联记录的最新 NAS 归档状态。切换“全部读数”后按提交顺序翻页，查询范围覆盖该配置相机的全部已保存读数；“导出状态 JSON”仍只是现有状态范围的导出，不是全历史打包。
